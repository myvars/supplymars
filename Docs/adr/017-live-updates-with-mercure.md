# ADR 017: Live Updates with Mercure: Private User Toasts and Resource Topics

## Status

Accepted (#116). Brings over the skeleton's pattern: its ADR 016 (private per-user toasts, myvars/skeleton#115) and ADR 017 (live pages on resource topics, myvars/skeleton#117), and the kit protections of myvars/skeleton#121. Those ADRs hold the history and the alternatives tried there; this one records what supplymars uses and where it differs. Amended in #144 (port of myvars/skeleton#136, decided in #141): refreshes on a page topic are public, and the cookie grants only the user's own topic and is set for staff only, so prefetch, other tabs and the hour no longer silence a live page.

## Context

FrankenPHP includes a Mercure hub ([ADR 016](016-frankenphp-in-place-of-nginx-and-php-fpm.md)), unused until now.

- **The order page goes stale.** While a staff user has `/order/{id}` open, the simulation changes it: purchase orders are accepted four times an hour, items shipped and delivered hourly (`MainSchedule.php`). The page shows none of it until reloaded.
- **A released lock goes unnoticed.** Any staff user can release any lock (`LockOrderHandler`), and the simulation skips a locked order: allocation (`CustomerOrderDoctrineRepository::findNextOrdersToBeProcessed`), acceptance (`PurchaseOrderDoctrineRepository::findWaitingPurchaseOrders`), shipping and delivery (`PurchaseOrderItemDoctrineRepository::findPurchaseOrderItemsByStatus`). The holder needs to know that automation can pick the order up again.
- **One flush raises many events.** Each simulation command flushes once per run (`AcceptPOsCommand`, `ShipPOItemsCommand`), so one flush can raise hundreds of status events across many orders. All of them are sync, and Audit, Pricing and the badge cache listen to them.
- **Two containers in production.** `php` serves pages; `messenger` runs the scheduled jobs and the `async` queue.

## Decision

### Shared: the skeleton's pattern

- **A publisher and a notifier** in `src/Shared/`: `LiveUpdatePublisherInterface` (`publish($topic, $turboStream)`, `refresh($topic)`) and `UserNotifierInterface` (`notify($userId, $type, $message, $url)`), implemented by `MercureLiveUpdatePublisher` and `MercureUserNotifier` (`Infrastructure/Notification/`). `refresh()` is **public** and `publish()` **private** (below). A hub failure is logged (`Live update not published`), never thrown. A toast is a `<twig:FlashToast>` (which gains an optional View link) appended to `#flash-container`, on the topic `user/{publicId}`. The notifier takes a plain string ID, because Shared imports from no business context.
- **One subscription point** in `base.html.twig`:
  - a permanent per-user element, which sets the request's one subscriber cookie, granting `user/{publicId}` only. Every page sets the same, so nothing the browser loads later (a hover prefetch, another tab) changes what a live page may receive. Staff only (`is_granted('ROLE_ADMIN')`): a customer receives no toasts and views no live page, so a customer's pages set no cookie, and a customer's login clears one a previous user left (`ClearMercureCookieOnCustomerLogin`). Without one the hub refuses every topic. A staff login needs no clearing: its next page sets the cookie for the new user;
  - a non-permanent element for the page's topics, inside `<turbo-frame id="body">`, because the order page is opened in that frame and a frame visit must drop the previous page's subscription;
  - `turbo-cache-control: no-cache` on a live page, and `#[Cache(noStore: true)]` on its action, so Back requests it again and shows what is current, rather than what the page held when it was left, until the next update.
- **Page refreshes are public; toasts are private.** A refresh carries no data, and each viewer's reload goes through the page's access check, so `refresh()` publishes with `private: false` and the hub sends it to any subscriber of the topic, whatever its cookie grants. Toasts (`publish()` on `user/{publicId}`) stay private, and a page topic never carries content: `publish()` there would reach nobody.
- **Any browser holding a token can receive any order's refreshes**: a staff user's, or one whose cookie outlived its login (below). The hub matches a subscription by topic, `*` or a URL pattern (`match_urlpattern=order/*`), and a public update goes to every subscriber that matches. A staff user can learn when an order changes, never what changed: the event carries no topic and no data. Staff see every order anyway, so this exposes nothing new. A signed topic name (Rails' `turbo_stream_from`) adds nothing, because a pattern does not need the name (myvars/skeleton#135).
- **A token is still needed.** The hub has no `anonymous` directive, so a subscriber needs a valid cookie: the page's stream stays `private` (`withCredentials`), customers get no cookie (and lose one left by staff when they log in), and logout (`ClearMercureCookieOnLogout`) ends the page's subscription as well as the toasts. Checked on both hubs in myvars/skeleton#136: a public update reaches a subscriber of its topic, of `match=*` and of a URL pattern; a private one to another user's topic does not; no token gets `401`.
- **The cookie lasts a week from the last page load.** `mercure.default_cookie_lifetime` is `app.login_lifetime`, the remember-me lifetime, and the token's `exp` follows it. The hub closes a connection at its token's `exp` and refuses the reconnect with `401`, after which a native `EventSource` may stop retrying, so an hour-long token silenced a tab left on one page, toasts included.
- **The page's access check guards the content.** Anyone with the cookie may receive a refresh, but what it loads comes through the order and purchase order pages' `ROLE_ADMIN` check, under each viewer's own login.
- **A refresh, not rendered HTML.** The order page differs by viewer (the lock button's label, the actions), and an update is built in the worker with no viewer. The refresh carries `method="morph"`; the page's own `turbo-refresh-method` stays `replace`. What the viewer is in the middle of protects itself with `data-turbo-permanent`, set from JavaScript only while it is open: `basic_modal` (an open modal, and the `<body>` scroll lock), `live_open` (the sidebar and help `Sheet`s and the user menu `DropdownMenu`), `live_toaster` (the toaster). The skeleton's `live_form` and its `inline_edit` change are not brought over: the order page has no form or inline edit of its own, only one-button POSTs and modals.
- **Logout clears the cookie** (`ClearMercureCookieOnLogout`).
- **The hub is on the site's origin everywhere**, so `connect-src 'self'` and the `__Secure-` cookie need nothing extra: FrankenPHP's own hub under `make up` and in production (a `mercure` block in the Caddyfile's `route`, `transport local`, one hub `name`, `resource_identifier {$MERCURE_PUBLIC_URL}`); a `dunglas/mercure:v1.1.4` container in `make up-dev-tools`, proxied by `symfony serve` (`.symfony.local.yaml`, `proxy_mercure`). One secret, `MERCURE_JWT_SECRET`, signs both tokens; the issuer is the fixed `MERCURE_JWT_ISSUER`.

### Order: where supplymars differs

- **The refresh goes through the queue, one per order.** The skeleton made its events async and refreshed from their handlers. Here that would change when the Audit, Pricing and badge listeners run. Instead a sync listener, `RefreshOrderPageForViewers`, resolves the order each event belongs to (the events carry their own IDs, so it asks the repository interfaces, Purchasing's included) and dispatches a `RefreshOrderPage` message to `async` with Messenger's `DeduplicateStamp`, keyed on the order, `onlyDeduplicateInQueue`. However many events a flush raises, the queue holds one refresh per order, and no request or scheduled job calls the hub. The lock is released when the worker receives the message, so a change made after that queues another.
- **The purchase order page shares its order's topic** (#120). `PurchaseOrderController::show` subscribes to `order/{id}` of its order, because the purchase order and item events the order page listens to already refresh that topic; a topic of its own would need a second refresh per change. The topic is named by `CustomerOrder::liveTopic()`, in Order's `Domain/`, so Purchasing's UI can use it under Deptrac. The page has no form or inline edit of its own: the rewind confirmation, each item's status edit and the status logs all open in the modal. The purchase order item page (`/purchase/order/item/{id}`) is not live: it is reached only by URL, nothing links to it.
- **Deduplication locks in Redis; every other lock stays on flock.** Deduplication takes a lock where the message is sent (`php`, or the scheduled job in `messenger`) and releases it where the message is handled (`messenger`). `LOCK_DSN=flock` could do neither: a flock key cannot be serialized onto the doctrine queue (`UnserializableKeyException`), and a file lock exists in one container only. `config/packages/lock.yaml` adds a `deduplication` store on the `snc_redis.default` client, the one the cache uses, which both containers reach, and `config/services.yaml` gives it to Messenger's `deduplicate_middleware` and `release_deduplication_lock_on_failure_listener`, which otherwise take the default factory. Tests use the `in-memory` store for it, and the test queue serializes its messages (`in-memory://?serialize=true`) as the real one does.
- **The events that were never raised now are.** `OrderItemWasCreatedEvent`, `OrderItemWasChangedEvent`, `PurchaseOrderWasCreatedEvent` and `PurchaseOrderItemWasCreatedEvent` existed but nothing raised them; `CustomerOrderItem::createFromProduct()` and `updateItem()`, `PurchaseOrder::createFromOrder()` and `PurchaseOrderItem::createFromCustomerOrderItem()` now do. `OrderItemWasChangedEvent` gets its own type, `ORDER_ITEM_CHANGED`, in place of `ORDER_ITEM_CREATED`.
- **An item removal event.** Removing an item (quantity 0 on the edit form) deletes it, so an event it raised could not be traced to its order. `CustomerOrder::removeCustomerOrderItem()` raises `OrderItemWasRemovedEvent` with the order's ID instead.
- **Purchase order quantity, removal and rewind events** (#118, #122). These changes raised no event, so they refreshed the order and purchase order pages only when they happened to change an order item's derived status. `PurchaseOrderItem::updateItemQuantity()` raises `PurchaseOrderItemWasChangedEvent` when the quantity changes. `PurchaseOrder::removePurchaseOrderItem()` raises `PurchaseOrderItemWasRemovedEvent` with its customer order's ID, as the order item removal does, because the purchase order is deleted too when it loses its last item. `PurchaseOrder::forceRewindToPending()` raises `PurchaseOrderWasRewoundEvent`. The rewind event is deliberately not a status change event: `PurchaseOrderRewindService` deletes the status logs the rewind reverses, so Audit must not log it.
- **A lock event.** `CustomerOrder::lockOrder($holder, $changedBy)` raises `OrderLockWasChangedEvent` (the order, the previous holder, the new holder or null, and who acted) when the holder changes. `LockOrderHandler` passes in the signed-in user as `changedBy`, because the holders alone cannot tell who released a lock. `NotifyLockHolderOfRelease` sends a `NotifyOrderLockReleased` message, through `async` without deduplication, only when a user loses a lock they held to someone else's action (released, or, outside the toggle, given to another holder); its handler tells the holder "Sam Carter released your lock on order #000123", with a View link. Taking a lock (the toggle only takes a free one), releasing your own, or a change with no previous holder sends nothing.

## Consequences

- Up to about 5 seconds between a change and the refresh: the worker's `--sleep=5`. In production a refresh caused by a scheduled job runs after that job, because one worker consumes `scheduler_default` and then `async` (`compose.prod.yaml`).
- Under `symfony serve`, live refreshes and toasts need the queue worker, as queued email does; `symfony serve` starts it (`.symfony.local.yaml`, #134).
- Each event costs the request or job one repository lookup and one Redis call; a duplicate is dropped there, before it reaches the queue. If Redis is down, sending fails, as sessions and the cache already do.
- A refresh dropped as a duplicate is not lost: the one queued before it has not been received yet, so the page it triggers shows both changes.
- If the worker is down, each order's lock frees itself after its TTL (300 s), so at most one refresh per order per five minutes queues up.
- Links on a live page prefetch on hover as on any other page.
- **No content on a page topic.** A public update with rendered HTML would reach every staff browser subscribed to `*`. Content goes through each viewer's private user topic, as toasts do.
- **The timing of a change is not private among staff.** If a page ever shows a record not every staff user may see, its refreshes still reach them all. That page needs the hub to check access: a token per stream (below), or private pattern grants in the cookie, once tested.
- **No revocation at the hub.** A user who loses staff access keeps a cookie until it expires and can keep receiving refreshes. Each makes the page reload, which the access check refuses, so nothing leaks.
- **The cookie can outlive a login.** It lasts a week from the last page load, and only logout clears it. A login that ends otherwise (remember-me expiring, an account removed or demoted) leaves the browser receiving its user's toasts and any order's refreshes for up to a week.
- A change to another purchase order on the same order also refreshes a purchase order's page: one quiet reload per job or action, and an order has only a few purchase orders.
- Fire-and-forget: no history. A missed refresh is fine, because the next visit shows the current state. A missed toast is lost.
- **The playground has one shared login** (`demo@supplymars.com`), so the holder and the releaser are always the same user and the lock toast never fires there. Live refreshes work as on live.
- **The simulation acts as `admin@supplymars.com`.** No console command changes a lock today. If one does, a system release would toast "admin released your lock"; `NotifyLockHolderOfRelease` says to decide then.
- The viewer's own action (lock, allocate) POSTs into the body frame and re-renders the page; the live refresh that follows finds nothing new.
- Each open logged-in tab holds one SSE connection to Caddy, served from Go, not a PHP worker. Production is a 2 GB box: note its memory before and after the first deploy, and check that the host Caddy streams `/.well-known/mercure` without buffering.
- Each stack's `php` container runs its own hub. `make up-prod-live`, `make up-prod-playground` and `make up-prod-local` refuse to start unless the env file sets `MERCURE_JWT_SECRET` (32+ characters), because FrankenPHP cannot parse its Caddyfile without it.

## Alternatives Considered

- **Publishing in the sync listener.** One hub call per event, inside the request or the scheduled job, with duplicates left to Turbo's 150 ms debounce in each browser.
- **Making the events async**, as the skeleton did. Changes when the Audit, Pricing and badge listeners run.
- **Collecting order IDs in memory during the flush** and dispatching once at the end. Needs a hook for the end of each flush and `ResetInterface` for worker mode; Messenger's deduplication does it with no state in a service.
- **Redis for every lock** (`LOCK_DSN`), with no service override. A Redis lock expires after its TTL, and `LockableTrait` sets the default 300 s with no refresh, so a backup or prune running longer would lose its lock part-way; flock holds it until the process ends. The rate limiter's locks would also become a Redis call per request.
- **`#[Broadcast]` on entities.** Puts UI in `Domain/` and broadcasts every Doctrine change rather than domain events. Page topics are public, but carry only a refresh.

Alternatives to public refreshes (#141, each weighed against: survives any later load, prefetch on, the same access guarantee, any project's access rules, both hubs, logout):

- **The page's topics merged into the one cookie** (#116 to #140). Every page response replaced the cookie with that page's grants, so a hover prefetch (hence a `turbo-prefetch: false` meta on live pages), a page loaded in another tab or the token's hour silenced a live page at its next reconnect.
- **A token per stream in an `Authorization` header**: a fetch-based SSE element, a token endpoint and a Voter per topic family. Meets everything, with the access check at the hub, but is a custom element and endpoint to keep. The fallback if a page needs the hub to enforce access.
- **One broad cookie on every page**, with URL-pattern grants for everything the user may see. Restates each page's access rule as a pattern, which only some rules can be.
- **Signed topic names** (`order/{id}/{hmac}`). Dropped in myvars/skeleton#135: a subscription to `*` or a URL pattern receives the public refresh without the name.
- **The union of the user's live topics kept in the session.** Outlives access that was taken away, and still expires.
- **The token in the stream's URL.** Mercure 1.0 removed it, and `access_token=` is not accepted.
- **No cookie on a prefetch response.** A prefetched live page then has no cookie, and other tabs still replace it.
- **Re-authorising the cookie before each reconnect.** Tabs race each other to set the one cookie.
- **The cookie for every logged-in user**, as the skeleton, where everyone is staff. Here customers log in too, and would receive every order's refresh timing with nothing to gain from a cookie.
